## Native skills are compatible as files, not as a universal command API

The original comparison below included Google's separately named Gemini CLI. The user clarified that their intended Gemini tool is `agy`, which identifies as Antigravity CLI. Preserve that executable and its native behavior; do not apply Gemini CLI commands or configuration to it merely because both can use Gemini models. Discovery paths and invocation surfaces differ:

| CLI | Relevant documented discovery | Native invocation / discovery check |
| --- | --- | --- |
| Codex | Project and user agent skill directories; the existing Superpowers plugin is separately installed in the Codex plugin cache | `$skill-name` or `/skills`; Codex's own terminal determines what is loaded. Root confirmed `$superpowers` autocomplete and the explicit `$superpowers:brainstorming` command in the web terminal. |
| Claude Code | `.claude/skills/<name>/SKILL.md`, user/project sources, and plugin-packaged skills. `--add-dir` can load skills from an added directory without editing settings. | Plugin skill commands are namespaced (for this install, `/superpowers:<skill>`); `/` shows commands. The installed plugin list and its component inventory confirmed the native Superpowers skills. |
| Antigravity CLI (`agy`) | Its native plugin and skill discovery; installed plugin components are staged under `~/.gemini/antigravity-cli/plugins/<plugin_name>/` according to current Antigravity docs | `/skills` is documented as browsing local/global workflows. `agy --help` supports interactive mode; a live menu was not reached because both tested directories required trust confirmation. Do not substitute `gemini skills list --all`. |
| OpenCode | `.opencode/skills`, `.agents/skills`, `.claude/skills`, their documented user-level equivalents, and optional `skills.paths` / remote skill sources | The documented agent surface is an on-demand native `skill` tool, with `available_skills` metadata and `skill({ name })` invocation. TUI `/` commands are a separate feature; no skill-to-slash-autocomplete behavior is claimed for the installed release. The flat user-level files are in a documented default root, but this installed CLI's inventory command did not confirm them. |

The existing Superpowers package cannot be assumed to activate in another CLI merely because its files exist under Codex's plugin cache. Claude's enabled native plugin is a separate, verified installation. Flat Superpowers skills are also present in `~/.agents/skills/`, a documented default source for Google's separate Gemini CLI and for OpenCode. That path alone does not prove discovery in the installed Antigravity CLI (`agy`). Even when discovered, skill files may depend on provider-specific tools, command names, agent handoff, approval behavior, or hooks. Discovery is not proof that a workflow can execute unchanged.

Superpowers deliberately includes workflow skills that tell the agent to use subagents. ORC's current product workflow has its own supervisor/peer boundary. A native skill that asks a CLI to spawn hidden agents can bypass that boundary; the skill should be reviewed and constrained for each provider rather than blindly forwarded as a universal capability. Provider-native subagents are not interchangeable with ORC's persisted peer session.

## Runtime compatibility and minimum adapter boundary

ORC's current runtime hardcodes `provider: 'codex'`, searches `ORC_CODEX_BIN`/`PATH` for `codex`, captures the native conversation UUID from Codex `/status`, resumes with `codex resume <UUID>`, and reads completed Codex history through Codex app-server. Claude, Gemini, and OpenCode are not registered providers today. The existence of an interactive CLI is insufficient to make it compatible with ORC restart recovery.

Keep skills and workflow execution inside the native CLI. ORC should not copy skills into provider homes, invent a shared `/skill` command, intercept tool calls, or add custom LLM tools to emulate provider behavior. A provider adapter should be limited to the lifecycle details ORC needs:

1. Resolve an explicitly configured executable and launch the provider's actual interactive TUI in a PTY with the repository as `cwd`.
2. Start a genuinely new native conversation, obtain its exact stable native ID from that process or a documented native API, persist the ID, then accept user input. Never infer an ID from a “latest” global session.
3. Forward and persist raw PTY output and input, resize events, exit state, and bounded startup/ready detection without suppressing approvals, tool calls, or skill output.
4. Resume only the exact persisted native ID after restart. Verify that the provider's native history is still available; otherwise report an unrecoverable session rather than silently creating another conversation.
5. Report provider/model/effort and the native skill/command surface only when confirmed from that session. Preserve each provider's approval and sandbox defaults; do not translate a generic ORC permission setting into an unsafe bypass flag.

### Provider-specific feasibility

- **Codex:** Implemented and end-to-end validated in ORC. The current adapter's bootstrap and history checks are Codex-specific.
- **Claude Code:** Feasible as the next candidate. The installed CLI supports interactive PTY sessions, an explicit `--session-id`, and exact `--resume <session-id>`. `--permission-mode plan` and `--restricted` are native controls, but an adapter must choose and validate an appropriate mode instead of assuming Codex's `-s read-only` semantics. Native Superpowers is already enabled here. A supervised same-ID restart test is still required before ORC can claim support.
- **Gemini / Antigravity CLI (`agy`):** This is the user's intended installed tool. Version `1.3.1` advertises native interactive mode, `--continue`, `--conversation <ID>`, `--project`, `--agent`, `--model` and `--effort`. Official docs describe `/resume` and `/skills`. This makes a native-terminal adapter a candidate, but neither skill execution nor same-ID restart recovery has been validated. Startup in both tested directories stopped at a trust gate, and the probes exited without changing it. Do not infer its lifecycle from the separate Google Gemini CLI.
- **OpenCode:** Feasible but structurally different: it has a native TUI, `--session <id>`, `serve` and ACP interfaces. The documentation also exposes session create/get/prompt APIs. For ORC's raw-terminal requirement, an adapter should attach the real TUI to a persisted exact session rather than replace it with API-generated assistant text. Validate how the installed release creates a durable new session before any task is accepted. The checked Codex plugin cache is not on the documented default paths, while flat skills are present in the documented `~/.agents/skills` root; the installed CLI inventory did not confirm them, and no custom OpenCode config was read or changed.

### Native skill-call probe

A bounded Claude print-mode probe was attempted from `/private/tmp`, using the installed `/superpowers:brainstorming` command, user settings only, plan permission mode, two-turn limit, no session persistence, and explicit denial of shell/edit/write tools. It exited before a model turn with `Not logged in`; no skill-call success is claimed. OpenCode's native `debug skill` inventory exited 1 and did not report the three checked skill names. Its safe auth-list command also exited 1, leaving auth status unknown. No OpenCode model call was attempted because an authenticated configured model was not established without reading provider configuration. These probes are separate from ORC's web workflow and do not validate any adapter.

Root supplied a separate successful Codex web-terminal check for native skill activation: in session `01a11af7-88d8-7b50-81e8-99f1272fcd11`, `$superpowers` autocomplete appeared, `$superpowers:brainstorming` injected the exact installed skill body, and two native turns completed. The response requested design approval; the run made no file edits and launched no peer. This proves that Codex skill activation can be forwarded through the web PTY while preserving the native CLI workflow. It is distinct from provider compatibility or recovery evidence for Claude, Gemini, or OpenCode.

OpenCode's native inventory diagnostic remained `Unexpected error` in default and `--pure` modes, in two working directories, even with verbose logging. Because that message provided no actionable cause and contained no sandbox or filesystem error signature, I did not request elevated execution. Its discovered-skill state remains unverified.

The practical next step is a shared adapter interface with three independent acceptance gates per provider: skill discovery in the native CLI, raw PTY interaction, and same-ID restart recovery. Passing one does not imply the others. Keep Claude/Gemini/OpenCode marked unsupported in UI and API until all gates pass.

## Evidence and primary documentation

Installed CLI outputs observed locally: Claude Code `2.1.294`, OpenCode `1.18.35`, Antigravity CLI (`agy`) `1.3.1`. The earlier `command -v gemini` result applies only to a separately named binary, not to the installed `agy` requested by the user. `claude plugin list` reported Superpowers enabled, version `6.4.1`, user scope; `claude plugin details` reported the 15-skill inventory. OpenCode `--help` exposed `serve`, `acp`, `session`, `attach`, and TUI commands. These are local observations, not statements that any non-Codex provider has passed an ORC workflow.

`agy` resolves to `/Users/tonamson/.local/bin/agy`, a small `bee-router-agy-wrapper` launcher for the installed Antigravity CLI. Only launcher identity and help/version were inspected; the referenced wrapper environment contents were not read. Bounded PTY probes selected “No, exit” at the trust gate, and the subsequent owned-process checks found no `agy` process remaining. A pre-existing TypeScript language server was left untouched.
